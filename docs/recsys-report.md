## Данные и воспроизводимость

Источник — [GroupLens MovieLens 100K](https://grouplens.org/datasets/movielens/100k/).
Исходный набор содержит 100 000 оценок 943 пользователей для 1 682 фильмов.
Оценки выставлены в 1997–1998 годах, диапазон — от 1 до 5.
Используются `u.data` (user, movie, rating, timestamp) и жанры/названия из `u.item`.
Порядок 19 жанров соответствует `u.genre`.
Данные о поле, возрасте, профессии и почтовом индексе не используются.
Лицензия разрешает исследовательское применение при указании источника,
запрещает перераспространение без отдельного разрешения и требует разрешения
для коммерческого использования. [Описание и лицензия GroupLens](https://files.grouplens.org/datasets/movielens/ml-100k-README.txt).

## Часть I Методы

Общие правила: положительным сигналом считается оценка 4–5, вес интереса равен
`max(rating − 3, 0)`. Пропуск в матрице означает отсутствие информации.
Фильмы с любой ранее выставленной оценкой не выдаются снова, включая оценки 1–3.
В сравнение входят только фильмы, имевшие хотя бы одну оценку в train.
Это общий набор кандидатов для всех четырёх методов.

**Content-based.** Фильм представлен бинарными признаками 19 жанров.
Каждый признак умножается на `IDF(g) = log((1 + N)/(1 + df(g))) + 1`, где
`N` — размер каталога train, `df(g)` — число его фильмов данного жанра.
Векторы фильмов нормируются по длине. Профиль пользователя — нормированная
взвешенная сумма векторов понравившихся фильмов. Балл кандидата равен
косинусной близости к профилю. Метод использует свойства фильмов, а не
похожесть пользователей. Жанры обеспечивают простое объяснение рекомендации.
Ограничения зависимости от признаков и повторения интересов согласуются с
[обзором Google](https://developers.google.com/machine-learning/recommendation/content-based/summary).

**Item-based collaborative filtering.** По train строится бинарная матрица
`B[u,i] = 1`, если пользователь поставил фильму 4–5. Для пары фильмов считаются
общие положительные пользователи `n_ij` и косинусная близость
`n_ij / sqrt(n_i × n_j)`. Чтобы совпадение одного пользователя не давало
слишком высокую уверенность, близость умножается на `n_ij/(n_ij + 10)`.
Диагональ обнуляется; для каждого кандидата остаются 40 ближайших соседей.
Балл кандидата — взвешенная сумма близости к понравившимся фильмам, делённая
на сумму весов истории. Параметры выбраны заранее для учебного решения,
а не подобраны на test. Подход использует коллективный сигнал о предпочтениях;
общая идея и различие явной/неявной обратной связи описаны в
[материалах Google](https://developers.google.com/machine-learning/recommendation/collaborative/basics).

**Популярность.** Эвристика ранжирует по сглаженному среднему рейтингу:
`P_i = (sum_ratings_i + 50 × global_train_mean)/(count_i + 50)`.
Это популярность с учётом качества оценок, а не просто число просмотров.
Пять звёзд от одного человека не должны обгонять устойчиво хорошие фильмы.
Предпочтения конкретного пользователя не учитываются, кроме удаления просмотренного.

**Популярность внутри жанра.** Та же формула применяется после фильтрации по
явно выбранному жанру. Если жанр не задан, берётся жанр с максимальной
взвешенной суммой положительных оценок в истории. Это прозрачная эвристика
для отдельной полки каталога. При отсутствии жанра и истории используется
общая популярность. Короткий список не дополняется фильмами чужого жанра.

Равные баллы разрешаются по популярности, затем числу оценок, затем ID фильма.
У content-based одинаковые жанровые векторы часто приводят к таким совпадениям.
Нулевые CF-баллы тоже упорядочиваются по популярности, и объяснение сообщает
об отсутствии похожего фильма. Внутренние баллы не являются вероятностями
или прогнозом оценки 1–5 и не сравниваются между алгоритмами.

## Методика оценки

Все оценки делятся по единой границе времени приблизительно 80/20.
Оценки со временем строго меньше границы входят в train; остальные — в test.
Одинаковые timestamps не разрываются. Используется глобальная граница, поэтому
обучение не видит более поздних оценок других пользователей. Популярность,
совместные оценки и IDF считаются исключительно по train.
История во время offline-оценки заморожена на момент этой границы.

Релевантные фильмы — test-оценки 4–5, которые доступны в общем train-каталоге
и не встречались в истории пользователя. Метрики считаются по пользователям,
имеющим историю train и хотя бы один такой релевантный фильм. Пользователи
без train-истории и новые фильмы посчитаны отдельно, а поведение cold start
проверено отдельной демонстрацией. Следовательно, основная таблица оценивает
сценарий для известных пользователей, а не качество всего будущего трафика.

Каждый алгоритм ранжирует весь непросмотренный доступный каталог; отрицательные
примеры не подвыбираются. Незамеченный фильм считается отсутствием попадания
в offline-метрике, но это не доказательство неприязни: пользователь мог его
просто не видеть. Средние метрики имеют одинаковый вес на пользователя.
Один временной разрез не заменяет проверку на нескольких периодах.

* `Precision@10 = число попаданий / 10`. Знаменатель остаётся 10 и для коротких списков.
* `Recall@10 = число попаданий / число релевантных test-фильмов пользователя`.
* `NDCG@10 = DCG/IDCG`, где попадание на позиции `j` имеет вес `1/log2(j+1)`.
  IDCG строится из `min(10, число релевантных)` попаданий в начале списка.
* `HitRate@10` — доля пользователей хотя бы с одним попаданием.
* Покрытие — число уникальных выданных фильмов / размер train-каталога.
* Жанровое разнообразие — средняя `1 − cosine` по всем парам жанровых IDF-векторов
  в списке. Это разнообразие жанров, а не измерение справедливости или сюжета.
* Полнота списка — доля пользователей с десятью выданными фильмами.

RMSE не используется: задача — выдача top-N, модели не предсказывают оценки.
Для разницы NDCG с эвристикой популярности дополнительно вычислен парный
bootstrap по пользователям: 2 000 повторов, seed 42, интервал 2.5–97.5 процентилей.
Это оценка неопределённости внутри данного test-среза; она не учитывает смену
времени, подбор моделей и смещение исходных данных.

## Фактические результаты

Граница времени: 1998-03-07T02:21:09+00:00 (Unix 889237269).
В train 79,999 оценок 751 пользователей, в test

Все методы выдали полный top-10 для каждого из этих пользователей.
Item-based CF дал максимальные Precision и HitRate, а жанровая эвристика —
максимальные Recall и NDCG. Простая популярность оказалась сильным baseline.
Content-based по одним жанрам хуже по попаданиям и даёт наиболее однообразные
списки: сходство по жанрам недостаточно для точного описания вкуса.
CF расширяет покрытие до 13.24% против 3.09% популярной выдачи, но это всё ещё
небольшая часть каталога; утверждать отсутствие смещения популярности нельзя.

значений. Для content-based интервал отрицателен в данном протоколе.
На следующем этапе полезнее улучшить признаки и проверить несколько временных
срезов, чем объявлять CF победителем по одному числу.

## Часть II a Проблемы подходов и способы улучшения

| Проблема | Предлагаемое решение | Недостаток решения и практический выбор |
| --- | --- | --- |
| Новый пользователь, нет положительной истории | Уже реализован переход к популярности; опционально предложить выбрать 1–3 жанра | Опрос увеличивает трение и отток, популярность не персональна. Не делать опрос обязательным, разрешить пропуск и обучаться на последующих действиях |
| Новый фильм и разреженность совместных оценок | Добавить content-based кандидаты, опираться на жанры/описание; исследовать гибрид | Плохие метаданные дают слабое качество; веса гибрида требуют validation. В нынешнем сравнении новые фильмы исключены ради общего каталога, а способность content-based работать с ними не измерена |
| Только 19 жанров, одинаковые профили | Добавить актёров, режиссёров, сюжетные признаки, затем сравнить с текущим baseline | Нужны права и качество метаданных, стоимость обновления; сложная модель хуже объясняется. Сначала измерить эффект нескольких понятных признаков |
| CF не использует явные отрицательные оценки как штраф | Добавить штраф за похожесть на оценённые 1–2 фильмы и проверить на validation | Негативный сигнал может относиться к одному фильму, а не жанру; чрезмерный штраф сужает интересы. Сейчас низко оценённые фильмы исключены из выдачи, но их свойства не подавляются |
| Популярность вытесняет редкие фильмы, возникает замкнутый круг | Ограничить долю популярных кандидатов, добавить exploration и разнообразие при reranking | Краткосрочная точность/CTR может снизиться, случайные рекомендации раздражают. Проверять удовлетворённость и покрытие вместе с качеством |
| Content-based и жанровая полка закрепляют прежний вкус | Добавить небольшую полку открытия нового, добровольные настройки жанров | Некоторые пользователи предпочитают предсказуемую выдачу. Сохранять объяснение и возможность скрыть рекомендацию |
| Накрутка оценок поддельными профилями | Проверять источник события, ограничивать частоту, выявлять синхронные профили, учитывать доверие | Фильтры ошибочно блокируют активных настоящих пользователей; проверка регистрации снижает конверсию. Сглаживание и shrinkage лишь уменьшают шум, но не обеспечивают защиту |
| Предпочтения могут раскрывать чувствительные интересы | Привязывать историю к авторизованному пользователю, ограничить доступ, сроки хранения и журналирование | Меньше данных ухудшает персонализацию и расследование ошибок. Demo-ID открыты только потому, что набор учебный; API нельзя переносить в production с произвольным user_id |
| Возрастные, лицензионные и этические ограничения | Применять ограничения доступности и возрастные правила до выдачи; аудировать жалобы и распределение показов | В MovieLens нет достаточных признаков для такой фильтрации; жанр не заменяет возрастной рейтинг. Нужен отдельный проверенный каталог, фильтры могут ошибаться |

Наличие реального исследования накрутки не доказывает отсутствие других уязвимостей.
Content-based меньше зависит от чужих оценок при основной сортировке, но подвержен
ошибкам метаданных и манипуляции ими; его разрешение одинаковых баллов использует
популярность. Поэтому он также не полностью независим от накруток.

## Часть II b Работа в production

| Проблема | Решение | Недостаток и способ контроля |
| --- | --- | --- |
| Медленный первый запрос | Загрузить и прогреть модель перед readiness, готовить snapshot offline | Запуск дольше; lru_cache в demo не гарантирует единственный fit при одновременных первых запросах. Прогревать до приёма трафика |
| Рост памяти и времени CF | Разреженные матрицы и хранение только top-neighbors, разделение retrieval и ranking | Здесь при fit строится плотная матрица O(items²); это приемлемо для 1 682 фильмов, но неприемлемо для миллионов. Урезание кандидатов может снизить recall |
| Повторные запросы и пик нагрузки | Кэш готовых списков, ограничение параллелизма, batch, контроль BLAS-потоков | Кэш устаревает, worker-процессы дублируют память. Измерять p95/p99 HTTP под нагрузкой, hit rate кэша и память |
| Устаревшие интересы и каталог | Обновлять историю, учитывать давность, регулярно пересобирать модель | Частый fit стоит дороже; decay может забывать устойчивые интересы. Версионировать каталог/модель, делать атомарную замену и rollback |
| Ошибки или задержки событий | Проверка схемы, дедупликация, контроль времени событий и задержки доставки | Легитимные повторы могут потеряться. Хранить идентификатор события и отдельную логику обновления оценки |
| Недоступна ML-модель | Сохранить последний валидный snapshot и подготовленную популярную выдачу | Fallback может замаскировать долгую деградацию. Логировать его долю и причину. В demo без данных возвращается 503; независимый production-кэш baseline ещё не реализован |
| Ошибки выбора модели или drift | Наблюдать метрики по версиям, shadow/canary, контрольные группы | Более сложная эксплуатация и выборка для сравнения. Откатывать при ухудшении ограничительных метрик |

В production полезно отделить поиск кандидатов, scoring и reranking для правил
доступности и разнообразия. Это соответствует
[архитектуре из курса Google](https://developers.google.com/machine-learning/recommendation/overview/types).
Здесь используется полный небольшой каталог и один процесс: это учебное локальное
развёртывание, не проведённый запуск сервиса для реальных клиентов.

## Часть III Мониторинг и бизнес-метрики

В demo реализованы `/health`, версия модели в ответе, явный fallback и измерение
времени рекомендаций в offline-эксперименте. Production-телеметрия, аутентификация,
пользовательские показы и A/B-тест описаны как следующий этап, они не заявляются
как уже проведённые.

План записи событий: `request_id`, версия алгоритма и каталога, псевдонимный user ID,
timestamp, item IDs и позиции показа; затем click, start, finish, skip, hide и complaint
с тем же request/exposure ID. Не сохранять сырую историю предпочтений в открытых
HTTP-логах. При расчётах учитывать повторные показы, ботов, задержанные события и
валидность факта видимого показа, иначе CTR окажется неверным.

| Уровень | Метрики | Как применять |
| --- | --- | --- |
| Сервис | HTTP p50/p95/p99, частота 5xx/503, пустых/коротких списков, fallback, readiness, RAM и время fit | Измерять отдельно cold и warm запросы. До пилота установить бюджеты задержки и ошибок, проверять алерты на нагрузочном тесте |
| Данные | Давность событий/каталога, пропуски, дубликаты, доля неизвестных пользователей и фильмов, распределение рейтингов | Сравнивать с предыдущим периодом и эталоном. Сдвиг сигнала не автоматически означает падение качества |
| Offline ML | Precision, Recall, NDCG и HitRate@10, покрытие и разнообразие | Пересчитывать на следующих временных срезах; сегментировать по длине истории и популярности объектов |
| Онлайн взаимодействие | CTR = клики / видимые показы; start rate = начатые просмотры / показы; completion = завершённые / начатые | Рост кликов без досмотра может означать кликбейт. Проверять конверсии на пользовательском уровне и доверительные интервалы |
| Бизнес | Время до выбора фильма, доля сессий с просмотром, 7/30-дневное удержание, отток, выручка на пользователя | Для подписочного сервиса цель — удобный выбор и долгосрочное удержание; чисел выручки в MovieLens нет |
| Ограничительные показатели | Скрытия, жалобы, нежелательный контент, жанровое покрытие, технические ошибки и задержка | Нельзя принимать прирост CTR ценой деградации удовлетворённости, безопасности или скорости |

Ожидание бизнеса: пользователь быстрее найдёт интересный фильм, чаще начнёт и
завершит просмотр, будет реже отменять подписку. Возможный фактический результат:
новая модель обгонит baseline по offline-NDCG, но ничего не изменит в удержании;
может повысить CTR и снизить досмотр или ухудшить задержку. Нельзя переводить
offline-NDCG в проценты роста продаж. На этом этапе измерена только offline-выдача.

План пилота: случайное стабильное распределение пользователей на контроль
(популярность) и эксперимент (выбранный метод), одинаковый интерфейс и каталог.
До начала выбрать основную метрику, минимальный практически значимый эффект,
уровень ошибки и размер выборки из реальной базовой конверсии; заранее задать
ограничения жалоб/задержки. Размер выборки здесь не выдумывается: нужного трафика
и дисперсии нет. Тест должен покрыть полные недельные циклы; решение принимать
по запланированной длительности, не останавливаясь при первом удачном результате.
Анализировать по пользователям, отдельно cold start, с доверительными интервалами.

## Ограничения выводов

Данные старые, отобраны активные пользователи (исходно минимум 20 оценок),
в них нет показов, кликов, покупок, лицензий и реальной доступности фильмов.
Каталог статичен; timestamp — время оценки, не просмотра. Оценка на одном периоде
и явных рейтингах не переносится автоматически на современный российский сервис.
Непросмотренные объекты не имеют достоверных отрицательных меток.
Параметры не оптимизировались; гипотезы улучшений требуют отдельного validation
и нового test. Локальная задержка не является SLA production.
